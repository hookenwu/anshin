# 人员档案（CarePeople）— Spec（待 Review）

状态：待 Review（不开发）
范围：为「谁说的」引入**轻量人员档案**，让重复输入同一个护工/护士/医生变快；**不扩展成通讯录**。
关系与兼容：**修订** `docs/care-notes.md`（§2 归属 / §4 模型：新增**可选**人员引用 + 历史姓名快照）；**不影响** `docs/record-center-spec.md`（记录中心结构、搜索、混排、SUPERSEDED 全部不变）。迁移：**v23 → v24**。

## 0. 设计原则（用户确认）

1. 人员**按 `CareRecipient` 隔离**，不做跨成员共享。
2. 字段**限定**为：姓名（必填）、性别、大致年龄、医院、医护公司、联系电话；其余仅为**必要的内部标识与时间字段**。**暂不增加停用状态**。
3. `CareNote` **可选**关联人员，并**保留 `attributionName` 作为历史姓名快照**；人员档案被修改或删除**不得改写历史笔记**。
4. `attributionType` **仍属于笔记**，**不由人员身份自动决定**。
5. 「谁说的」处支持**搜索选择已有人员**、**快速新增人员**，同时**保留自由输入**。
6. **优先保证新增笔记流程顺畅**：人员管理不得给记录流程增加负担。
7. 迁移、成员隔离、删除行为与回归测试自行设计；**不扩展成完整通讯录**。

## 1. 领域模型（v23 → v24）

`care_people`
| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | Long PK autoGenerate | |
| `careRecipientId` | Long | NOT NULL，FK → `care_recipients` ON DELETE CASCADE（**成员归属的唯一事实源**） |
| `name` | String | NOT NULL（必填；**用户输入什么就是什么，不做规范化**） |
| `gender` | String? | 男 / 女 / 其他 |
| `approxAge` | Int? | **大致年龄**（刻意不叫"年龄"，不逼精确值；仅做宽松范围校验） |
| `hospital` | String? | 医院（自由文本） |
| `agency` | String? | 医护公司（自由文本） |
| `phone` | String? | 联系电话（自由文本，仅存本机、不校验格式、不外发） |
| `createdAtMs` | Long | NOT NULL |
| `updatedAtMs` | Long? | |

索引：`careRecipientId`、`name`（供选择器搜索）。
**不加** `isArchived`（原则 2）：不再使用的人**直接删除**，历史由笔记里的姓名快照保护（见 §2）。

`care_notes` 新增一列
| 字段 | 类型 | 约束 |
|---|---|---|
| `attributionPersonId` | Long? | 可空。**不建外键**（理由见下） |

**为什么这一列不建外键**（表述修正：SQLite **允许** `ALTER TABLE ADD COLUMN` 带 `REFERENCES`，**前提是该列可空且默认值为 NULL**——本列两条都满足，所以"技术上不可行"的说法是不准确的）。本设计**仍然选择不加外键**，理由有三：
1. **不需要**：历史由 `attributionName` 快照保护，外键唯一可能带来的便利（`ON DELETE SET NULL`）并非必需——人员删除后我们本来就要**容忍悬挂并保留快照**；
2. **一致性**：本仓对跨实体引用一律**无外键 + 读取容忍**（`CareTodo.source*`、`care_note_links.targetId`），本列与之同源；
3. **迁移最省**：保持**纯新增**（`CREATE TABLE` + `ADD COLUMN`），避免在 `care_notes` 上叠加跨表级联语义。
→ **迁移保持纯新增，无表重建、零数据搬运。**

**字段语义边界**：人员是**归属来源**，不是"笔记所关于的对象"——因此**不进入 `care_note_links`**（后者的 `targetType` 仍是 `MEDICATION`/`CARE_TASK`/`TODO`），两者的语义必须分开。

## 2. 历史与删除行为（核心规则）

| 事件 | 规则 |
|---|---|
| 人员**改名** | 既有笔记**不回改**（`attributionName` 是**当时的快照**）；仅**新**笔记使用新名字 |
| 人员**删除** | 档案行删除；**笔记一行不动**，继续显示当时的名字；`attributionPersonId` 成为**悬挂指针** |
| 选中人员后**手动改姓名** | **自动解除人员关联**（清空 `attributionPersonId`），并**保留用户新输入的姓名**——不把名字改回该人员档案的名字（用户的手改优先） |
| **保存笔记时二次校验** | 重新校验**人员存在**且**属于当前成员**；不满足则**不写入关联**（**禁止跨成员关联**），并**保留姓名快照** |
| 悬挂指针读取 | **容忍**：渲染快照名、不报错、不影响笔记任何其它行为 |
| 悬挂指针清理 | **不做后台清理**；该笔记**下次保存**时**确定性地清空**无效 ID，且**不改写历史姓名** |
| 成员**删除** | `care_people` 级联删除（与其笔记一并随成员级联），无悬挂残留 |
| **不得发生** | 任何代码路径因人员改名/删除而改写笔记正文、`attributionName` 或 `attributionType` |

## 3. 与 `attributionType` 的关系（原则 4）

- `attributionType`（`CLINICIAN` / `CAREGIVER_EXPERIENCE` / `PERSONAL_OBSERVATION` / `EXTERNAL_MATERIAL`）是**这条笔记的语境**，**不随所选人员自动设置、也不由人员身份推导**。
- 同一个人（如"护士张"）在不同笔记里可以是「医护交代」也可以是「照护经验」——**人员不携带类型**。
- 既有规则不变：类型**在任何展示面恒可见**、默认 `PERSONAL_OBSERVATION`、个人观察保持中性框架。

## 4. 交互（原则 5、6）

**4.1 「谁说的」输入处**（笔记编辑器）
- 默认可**自由输入**（`attributionName` 路径**完全保留**，不填档案也能记录）；
- 同时提供**选择器**：输入即**搜索**当前成员的已有人员（按 `name` 匹配，前缀/包含皆可），点选后填写该人员；
- 提供 **「＋ 新增人员」**：只填**姓名**（必填）+ 可选字段（性别/大致年龄/医院/医护公司/电话）→ **保存后自动选中**，**不离开笔记编辑流程**（原则 6）；
- 选择器**按当前 `attributionType` 做排序提示**（如选了「医护交代」优先展示既有医护）——**仅排序，不锁定、不自动改类型**；
- 提示文案保持中性，不暗示"选了医护就等于医嘱"。

**4.2 人员档案管理**：`更多 → 人员档案`（列表 + 新增/编辑/删除）。**不新增底部 tab**、**不改记录中心结构**；列表仅展示姓名 + 次要信息，点击编辑，删除走既有破坏性确认写法。

**4.3 记录中心**：**零改动**。搜索仍匹配 `attributionName`（快照名）→ **按人名搜索历史笔记仍可用**，不因引入档案而变化。

## 5. 迁移与成员隔离

- **迁移 v23 → v24**：`CREATE TABLE care_people` + 2 个索引 + `ALTER TABLE care_notes ADD COLUMN attributionPersonId`（可空）——**纯新增，无表重建**。
- 配套（本仓反复踩过的坑，逐项必做）：`DatabaseSchema.VERSION` → 24；注册 `MIGRATION_23_24`；导出 `24.json`；`RoomModelContractTest` 版本断言改 24；**`MedLogDatabaseMigrationTest` 及其它 androidTest 里所有硬编码迁移列表全部补齐**；新增 `CarePeopleMigrationTest`（种一个带数据的 v23 库 → 迁移 → 断言：旧数据零丢失、新表可写、索引存在、删除成员级联人员、`care_notes` 旧行 `attributionPersonId` 为 NULL）。
- **成员隔离**：仓储完全沿用既有约定——按 `ActiveRecipientStore` 作用域；`NO_RECIPIENT` 时**读返回空、写抛错**；人员查询永远带 `careRecipientId`。
- **备份兼容**：上界随 `VERSION` 自动放行（`BackupCompatibilityPolicyTest` 的钉桩随版本更新）；旧版本 App 无法打开新备份属既有约束。

## 7. 实施范围（分阶段）

- **P1 数据层**：`care_people` + `care_notes.attributionPersonId` + DAO + 仓储（成员作用域）+ 迁移 + 迁移/隔离/级联/快照回归测试。
- **P2 记录流程**：编辑器「谁说的」选择器（搜索 + 快速新增 + 自由输入保留）+ 按类型的排序提示 + 悬挂指针的保存时清理。
- **P3 管理面**：`更多 → 人员档案` 列表与表单（新增/编辑/删除 + 破坏性确认）。
- **不做**：跨成员共享、停用状态、通话/记录/头像/关系图/自动合并/AI 推断、通讯录式详情页、任何"人员决定笔记类型"的逻辑。

## 8. 验收标准

1. **记录流程不被拖慢**：不选人员也能保存笔记（自由输入路径可用）；「＋ 新增人员」后**自动选中并回到笔记编辑**，无需二次操作。
2. **快照不可变**：改人员姓名后，**历史笔记仍显示旧名**；删除人员后，**历史笔记照常显示当时的名字**（不能出现空归属——归属类型与姓名在任何展示面都必须可见）。
3. **类型独立**：人员不改变、不预设 `attributionType`；默认仍为 `PERSONAL_OBSERVATION`。
4. **成员隔离**：人员仅属当前成员；`NO_RECIPIENT` 读空/写抛错；删除成员级联人员，且其笔记不残留悬挂。
5. **迁移**：v23 → v24 **零数据丢失**、无表重建；`24.json` 与迁移 SQL 一致；**所有**硬编码迁移列表已补。
6. **搜索**：按人名可搜到历史笔记（经 `attributionName` 快照）；选择器可搜到已有人员。
7. **回归**：记录中心、服药、照护事项、待办、首页组合行为不变（首页 dump 与改造前一致；登记表无新增条目）。

## 9. 已确认决策与冻结说明

1. 「大致年龄」使用**可选整数**。
2. 删除人员时**提示关联笔记数量**（如"有 N 条笔记记录了此人，删除后这些笔记仍保留其姓名"），但**不阻断删除**。
3. 管理入口定在 **`更多 → 人员档案`**。
4. 冻结前补齐的三条边界（已写入 §1 与 §2）：① 选中人员后**手动改姓名**→ 自动解除人员关联、**保留新输入的姓名**；② 保存笔记时**二次校验人员存在性与成员归属**，禁止跨成员关联，失败时**保留姓名快照**；③ 悬挂引用**读取容忍、不做后台清理**，**下次保存时确定性清空**无效 ID 且**不改写历史姓名**。
5. §1 的表述已修正：SQLite **允许** `ADD COLUMN` 带 `REFERENCES`（列可空 + 默认 NULL）；本设计仍不加外键，理由已改为 §1 所列三条。

**本文件已冻结**：字段不扩、功能不增；如需模型级改动须新开评审。实施按 §7 的 P1 → P2 → P3 推进。
