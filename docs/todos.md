# 待办事项（Todo）— SDD 规格

状态：待实施（本文件先定方向，不动代码）
决策基线：用户已确认「方案 B：Todo 作为独立一等实体，不并入 CareTask」。
关联阅读：`docs/care-tasks.md`（照护事项）、`docs/dose-strength.md`（剂量/规格）。

## 0. 用户已拍板的决策

1. **独立一等实体** `care_todos`，不并入 CareTask、不并入 Medication。
2. **首页顶部**：默认最多 **3 条** + 「查看全部 n 条」；**安静但显眼**。
3. **可选截止日期**，但 **MVP 不接闹钟**（不产生通知、不占提醒编号空间）。
4. 完成后**从首页消失并进入历史**，**支持撤销**。
5. **状态机收敛**：不使用语义模糊的 `CLOSED`；采用 `OPEN / DONE / CANCELLED`（见 §2.2）。
6. **预留轻量来源关系** `sourceType? / sourceId? / sourceNote?`，但本期**不开发**自动规则、AI 联动或复杂关联。
7. 待办**不进** TodayItem 时间轴、**不进**今日计划进度/依从率、无重复排期、默认无通知。

## 1. 语义界定（它到底是什么）

待办 = 「观察 → 建议动作 → 闭环」的**一次性跟进项**：无作息、不重复、可能有截止、通常带来源（护工反馈 / 家人发现 / 症状日记）。

- 不是用药（无剂量、无库存、无服药记录）；
- 不是照护事项（无排期、无重复、无时长、无"按需"语义）；
- 是**派生的跟进项**：来源可以是一条观察或症状记录，去向是"办完了 / 决定不办"。

术语约定（避免与既有概念混淆）：中文一律叫「**待办**」；**不要**叫"任务"（会与 CareTask 的「照护事项」撞车）；「照护事项」专指 CareTask。

## 2. 领域模型

### 2.1 实体 `care_todos`

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | Long PK autoGenerate | — | |
| `careRecipientId` | Long | NOT NULL，FK → `care_recipients(id)` ON DELETE CASCADE | 成员隔离，与既有实体同约定 |
| `title` | String | NOT NULL | 待办正文，如「让护士看一下压疮风险」 |
| `status` | String | NOT NULL，默认 `OPEN` | `OPEN` / `DONE` / `CANCELLED` |
| `dueAtMs` | Long? | 可空 | 可选截止时刻；**逾期是派生量，不落库**（见 §2.2） |
| `sourceType` | String? | 可空 | 预留：`OBSERVATION` / `SYMPTOM` / `HEALTH_RECORD` / `AI_SUGGESTION` 等；**MVP 只存不解读** |
| `sourceId` | Long? | 可空 | 预留：来源记录 id；**不做外键、不做级联**（见 §2.4） |
| `sourceNote` | String? | 可空 | 来源备注/原文摘要，如「护工：骶尾处发红」 |
| `createdAtMs` | Long | NOT NULL | |
| `closedAtMs` | Long? | 可空 | DONE/CANCELLED 时写入；**撤销回 OPEN 时必须清空** |
| `resolutionNote` | String? | 可空 | 可选：怎么处理的 / 为什么取消 |

索引：`careRecipientId`、`status`。

**刻意不加的字段**（每条都说明理由，避免将来"顺手补上"）：
- **不加 `isArchived`**：终态（DONE/CANCELLED）本身即"已关闭"，历史可查；再加归档等于两套关闭语义。这是与 Medication/CareTask 的**有意分歧**。
- **不加 `linkedCareTaskId`**：唯一的跨实体引用会悬空（照护事项被删后指向不存在的 id）；MVP 不需要"转成照护事项"，等真要用再加（届时按 §2.4 的容错约定处理）。
- **不加 `priority`**：排序由截止与状态派生，够用；加字段会诱导出一套优先级 UI。
- **不加 `assignee`/责任人**：本期不做多用户与分工（用户第 6 条决策）。

### 2.2 状态机（三态，语义互不重叠）

```
        ┌──────────────────────────────┐
        │ OPEN（未闭环，需处理）        │
        └───┬───────────────────┬──────┘
   DONE（已处理完）        CANCELLED（不再处理）
            └──── 撤销 ────────────┘  → 回 OPEN（并清空 closedAtMs）
```

- **为什么是三个而不是两个**：`DONE` 与 `CANCELLED` 语义确实不同——前者是"动作真的做了"（将来算跟进完成率时应计入完成），后者是"决定不做/不需要了/误报"（既不算完成也不算逾期）。二者都以"从首页消失"为共同表现，但**历史里必须可区分**，否则将来做"跟进闭环率"时会算错。
- **为什么去掉 `CLOSED`**：它只能表达"不再显示"，无法区分"做了"和"不做了"，是模糊态；按用户要求拆成 DONE / CANCELLED。
- **`OVERDUE` 不是状态**：`status == OPEN && dueAtMs != null && dueAtMs < now` 的派生判定，只在渲染时计算。理由：落库需要后台定时翻转（Android 上没有可靠的"到点改状态"机制，得引入 WorkManager 定时扫描），既增加成本又会产生不一致。**无 `dueAtMs` 的待办永不逾期**。

### 2.3 完成/撤销的落库规则

- 完成：`status = DONE`，`closedAtMs = now`。
- 取消：`status = CANCELLED`，`closedAtMs = now`。
- 撤销：`status = OPEN`，**`closedAtMs = null`**（必须显式清空，否则历史统计自相矛盾）。撤销入口不做窗口限制：在历史里随时可撤销。
- 重复点击必须幂等（同一状态再点不产生新行、不改时间戳）。

### 2.4 来源关系的预留约定（防未来挖坑）

- `sourceType` / `sourceId` / `sourceNote` 是**提示性元数据**，不是外键：
  - 不建 FK、不做级联删除；
  - 来源记录被删/找不到时，**忽略即可**（不报错、不自动删待办、不清空备注）；
  - 不因为来源存在就改变待办的状态或展示（**本期不解读 sourceType**）。
- 未来若做"从观察自动生成待办"（P4），仍沿用这套字段，届时再定义 `sourceType` 的取值表与去重规则（例如同来源同日不重复生成）。

### 2.5 成员作用域

与 `CareTaskRepositoryImpl` 完全同约定：
- 全部读写按 `ActiveRecipientStore` 当前成员过滤；
- `NO_RECIPIENT = 0L` 时**读返回空、写抛错**；
- 成员删除 → FK CASCADE 连带删除其待办（补测试）。

## 3. 首页信息架构

区块顺序（自上而下）：

```
HomeHero（今日计划进度 18 次 / 已服…）        ← 保持第一，不动
【待办】区块（未闭环）                          ← 新增
低库存横幅 / 相互作用横幅（如有）
筛选 chips（全部/用药/照护/…）
「今日计划」时间轴（按时间混排）
按需照护区块（AS_NEEDED）
PRN 区块（按需用药）
```

- **待办区块放在 hero 之后、时间轴之前**。理由：hero 是"今天几次药、吃了几次"的一眼摘要，属安全关键；文献里唯一的临床任务排序规则（Cerner CareCompass）也是**按紧迫性**排（逾期置顶、已排程在前、未排程在后），而不是"未定时项一律压过定时项"。待办要在"打开就看到"的意义上置顶，但不压过进度摘要。**这一条是设计假设，不是文献结论**——建议真机用一阵再定。
- 区块内部顺序：`逾期` > `今天截止` > `其他（无截止，或截止在未来）`（同级按 `createdAtMs` 升序，早的在前）。<br>实施澄清：截止在未来的待办**仍会出现在区块里**（它同样是未闭环的工作），只排在"今天截止"之后；因区块有 3 条上限且按紧迫性排序，未来项不会挤掉逾期/今日项。
- **默认最多 3 条**，其余收进「查看全部 n 条」（跳待办列表页）。逾期条目用醒目色，**但不响铃、不推送**。
- **空态：一条未闭环待办都没有时，整个区块不渲染**（不留空标题、不留占位）。
- 待办**只显示 `OPEN`**；`DONE`/`CANCELLED` 只在历史里出现。
- 入口：区块内一个「+ 新建待办」；列表/历史页放**「更多」菜单**里（**不能新增底部 tab**——`NavigationHierarchyTest` 把顶层目的地钉死为 5 个，T6 时已踩到）。

与现有机制的隔离（必须写死，防止将来被"顺手合并"）：
- **不进** `todayItems` → 因此**不进** `overallTotal` / `overallHandled` / hero 进度 / 常驻进度通知；
- **不进**"现在要做"区块（它按 `scheduledMinuteOfDay` 过滤，待办无此字段）；
- **不进**依从率（`MedicationAdherence` 只读 Medication + 服药日志）；
- **不进**提醒登记表 / 通知 / `reconcileAll`（无编号空间、无闹钟）；
- **不进**"历史/服用记录"页（那是服药历史）；待办历史放在待办自己的列表页内（进行中 / 历史 两个 tab）。

## 4. 迁移（v21 → v22）

- **纯新增表**：`CREATE TABLE care_todos (...)` + `CREATE INDEX index_care_todos_careRecipientId`、`index_care_todos_status`；照 `MIGRATION_19_20`（新增 `care_tasks`/`care_task_logs`）的先例，**无需表重建**、**不触碰任何既有表与数据**。
- `DatabaseSchema.VERSION` 21 → 22；注册 `MIGRATION_21_22` 到 `AppModule.provideDatabase.addMigrations(...)`；导出 `22.json`。
- **必须同步的既有测试**（上次踩过）：`MedLogDatabaseMigrationTest` 里有**多处硬编码的迁移列表**，全部要加 `MIGRATION_21_22`；`RoomModelContractTest` 断言 `VERSION == 21` → 改 22。
- **备份兼容**：`BackupRestoreUseCase.canRestore` 的上界跟着 `VERSION` 走，自动放行；但**旧版本 App 无法打开新版本备份**——这是任何 schema 变更都有的既有约束，不是本特性的缺陷，特此记录以免日后误报。
- 迁移测试断言：v21 有数据（药品/照护事项/日志/成员）→ v22 后数据零丢失、`care_todos` 存在且可读写、索引存在、成员删除级联。

## 5. 与现有实体的边界（对照表）

| 维度 | Medication | CareTask（照护事项） | **Todo（待办）** |
|---|---|---|---|
| 本质 | 用药计划 | 可重复的照护干预 | 一次性跟进项 |
| 排期 | 作息/频次/间隔 | FIXED_TIMES/INTERVAL/AS_NEEDED | **无排期**，可选截止 |
| 重复 | 有 | 有 | **无** |
| 提醒 | 有（闹钟+通知） | 有（按需除外） | **MVP 无** |
| 记录 | 服药日志（剂量/部分服用） | 完成日志（起止/时长/体位） | 仅状态与关闭时间 |
| 进今日计划进度 | 是 | 是（按需除外） | **否** |
| 进依从率 | 是 | 否 | **否** |
| 终态 | 归档 | 归档 | DONE / CANCELLED |
| 首页位置 | 时间轴 / PRN 区块 | 时间轴 / 按需区块 | **顶部待办区块** |

**不动**：Medication、CareTask、提醒链路、统计、Widgets（小组件的归档残留风险是既有问题，另案处理）。

## 6. 分阶段任务

- **P1 数据层**：实体 + DAO + 仓储（成员作用域）+ 迁移 v21→v22 + 迁移测试 + 成员隔离/级联测试。
- **P2 首页区块**：待办区块（未闭环 / 逾期高亮 / 封顶 3 条 + 查看全部 / 完成 + 撤销）+ 空态不渲染 + 契约测试。
- **P3 列表与编辑**：待办列表页（进行中 / 历史）+ 新建/编辑（标题 / 可选截止 / 来源备注）+ 关闭与撤销 + 「更多」菜单入口。
- **P4（后续，本期不做）**：截止前轻提醒（需先修"删除后登记表残留"缺陷并新增编号空间）；从观察/症状记录生成待办（启用 `sourceType` 解读与去重规则）。

## 7. 验收

1. P1：单测 + 设备端 instrumentation（含 v21→v22 迁移、成员隔离、级联删除）；
2. P2：首页区块三条以内正常、第 4 条进「查看全部」、逾期高亮、完成后消失、撤销后回到顶部；**且**今日计划进度（如"18 次"）、时间轴、按需区块、PRN 区块**逐项与改造前一致**（回归门禁）；
3. P3：新建/编辑/关闭/历史/撤销全链路；无待办时首页**看不到任何待办痕迹**；
4. 全局：无新增通知、无新增闹钟（可用登记表 + `dumpsys alarm` 计数证明）。

## 8. 非目标

闹钟式提醒（P4）、重复待办/子任务/多步流程、责任人分配与多用户、自动规则与 AI 联动、把待办并入 CareTask 或 Medication、改动依从率口径、把待办历史并进服药历史页。

## 9. 待决与风险

1. **待办区块位置**（hero 之后 vs 最顶）属设计假设，无文献支持，建议真机试用后定。
2. **封顶 3 条**是拍的数；真机上若常被「查看全部」截断，可调或改为自适应。
3. **来源关系**只预留不解读；将来做自动生成时需补去重规则与 `sourceType` 取值表。
4. 若将来要待办提醒：必须先修"照护事项删除/归档后登记表残留 `1:task:1`"的既有缺陷（同一清理路径），否则新类型会复制同样的泄漏。
